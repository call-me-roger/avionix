# 737 CDU

| Field | Value |
|---|---|
| ID | `F-51` |
| Stage | `4` |
| Category | Aircraft-specific |
| Status | Proposed |
| Depends on | `F-32`, `F-03` |
| Competitor prevalence | Matrix count 4 of 12 representative products (`research/competitors.md`). Wider set: 5 of 13 researched companion products offer a Zibo CDU (WebFMC, AirFMC, XPlaneCDU, X-CDU, Flight Deck FMS); Remote X-Plane Avionics offers the stock 737-800 CDU only |

## Summary

Avionix shows the Zibo or LevelUp 737 CDU screen on a phone or tablet and sends key presses back to
it, so route entry and en-route checks happen on a second device instead of a popup over the
outside view. The feature is conditional: it can only be built if the aircraft publishes its CDU
screen as datarefs, which the research does not confirm and which must be verified first.

## Why now

The CDU is the most-requested 737 panel: more third-party tools and forum threads than any other,
and five researched products ship one [1]. F-32 establishes CDU behaviour for the default FMS using
Laminar's documented screen datarefs [2]; this applies the same shape to the aircraft most Avionix
users fly. It sits in Stage 4 because the data source is unproven.

## User stories

- As a 737 pilot, I want the CDU on my tablet so that programming a route does not cover the
  windscreen or force me into a zoomed cockpit view.
- As a prospective user, I want to be told plainly whether my add-on and version is supported,
  before I rely on the CDU in flight.

## Scope

### In scope

- A verification task, done first on a pinned Zibo version: does the aircraft expose its CDU screen
  lines (and any style or colour) as readable datarefs, and its keys as commands or writable
  datarefs? The answer is recorded here before the rest is committed.
- If yes: a mirror of the CDU screen refreshed from the simulator, with colour or emphasis where the
  aircraft publishes it, and the full key set (line select keys, keypad, page and function keys,
  EXEC, DEL, CLR, brightness), each sending its press to the aircraft.
- Selection between the captain and first officer CDU where both are exposed, and a statement of
  which add-on version the mapping was tested against.

### Out of scope (this feature)

- Any flight-management logic of Avionix's own: the app mirrors and presses keys, the aircraft
  computes. The Web API has no flight-plan upload endpoint and no navdata queries, so a route
  cannot be pushed in any other way [3].
- The default FMS CDU (F-32), the Airbus MCDU (F-57), plan progress (F-31), import/export (F-33).
- Any in-simulator plugin, bridge or screen capture. If the CDU is reachable no other way, this
  feature is not built.

## Functional requirements

R1. Before implementation, a verification run against a pinned Zibo version records which CDU
screen and key names exist, their types, and whether they are readable and writable. If no screen
datarefs exist, the feature is closed as not feasible under the Web-API-only constraint, and the
app offers no 737 CDU rather than a broken one.

R2. Given screen datarefs, the app shows the CDU screen as the aircraft renders it, with no
client-side interpretation of page content.

R3. Each key sends exactly one press per tap, in the order tapped, and the visible result is
whatever the aircraft does with it; the app reports if it cannot keep up rather than dropping taps.

R4. Where the aircraft publishes per-character style or colour the mirror reproduces it; where it
does not, the screen uses one legible style and the app invents no emphasis.

R5. The panel names the detected aircraft and the version the mapping was tested against, and says
when the loaded version differs.

R6. When a key name cannot be resolved the affected key is marked unavailable in plain language and
the rest of the CDU keeps working; when the screen itself cannot be resolved, or the aircraft is
not a recognised 737, the feature is not offered and the app says why in one sentence.

R7. On disconnection the screen is marked stale within one second and no key accepts input; on
reconnection every name is resolved again before the panel becomes live, because ids are
session-scoped [3].

R8. A key press the simulator rejects produces a short message naming the key and the fact that the
aircraft refused it. No raw protocol error, endpoint or payload is shown; tokens are never logged.

## X-Plane Web API mapping

Reads (screen) and command activations or writes (keys) only, at the Web API's ~10 Hz subscription
rate.

| Purpose | DataRef / command | Type, units | Read/Write | Source |
|---|---|---|---|---|
| Default FMS screen text and style (not used by Zibo) | `sim/cockpit2/radios/indicators/fms_cdu1_text_line0..15`, `fms_cdu2_text_line0..15`, matching `..._style_line0..15` | string, 24 chars; style bytes | R | Laminar [2] |
| Zibo CDU screen lines | possibly a `laminar/B738/fmc1/Line...` family (unverified, community; one report cites it, another found no confirmed names) | unknown | R | [4], [5] |
| Zibo CDU keys (LSK, keypad, page, function, EXEC, DEL, CLR, brightness) | not identified; verify in `B738_Commands.txt` shipped with the aircraft | — | W | [6] |
| Captain / first officer CDU selection | not identified; verify in DataRefs.txt | — | R/W | [6] |

Zibo does not use Laminar's `fms_cdu*` datarefs: its CDU is custom rendered, and the open-source
Zibo CDU client reaches it through a third-party UDP plugin, not the Web API [5]. That route is
outside Avionix's scope; the first row is listed only to say which mechanism does not apply.

## Aircraft compatibility

The default X-Plane FMS is covered by F-32 through Laminar's documented screen datarefs [2]. This
feature covers Zibo and LevelUp only, subject to R1. Other payware FMSs publish their own
non-standard sets and are out of scope; the Airbus case is F-57. The same verification run confirms
whether the stock 737-800 CDU is already covered by the default-FMS mapping.

## Competitor evidence

- The CDU has more third-party tools and dedicated forum threads than any other 737 panel —
  https://forums.x-plane.org/forums/topic/118712-remote-cdu-on-ipad-safari-browser/
- WebFMC's free tier is Zibo-only, and its reviewer calls the remote-device workflow "much easier
  and better" than the in-simulator popup —
  https://www.x-plained.com/utility-review-green-arc-studios-webfmc/
- Every product in this category reads per-line CDU text datarefs and renders them client-side;
  none screenshots the simulator —
  https://developer.x-plane.com/article/datarefs-for-the-cdu-screen/
- The open-source Zibo CDU client states that the default 737 does not support the standard
  datarefs and that other aircraft use non-standard ones; it was later unpublished from Google
  Play, with users reporting "very slow response when clicking CDU buttons" —
  https://github.com/waynepiekarski/XPlaneCDU
- A free browser tool runs the stock 737-800 CDU over the native Web API with no plugin, with 737
  support labelled initial —
  https://forums.x-plane.org/files/file/101030-remote-x-plane-avionics-a330-mcdufcuefis-737-cdu-for-tablet-browser/

## Acceptance criteria

- [ ] The verification run is recorded here, naming every CDU dataref and command found or stating
      that none exist, before any implementation is merged.
- [ ] On the mock server the mirror renders supplied text, marks itself stale on disconnection and
      blocks key input while stale; on a real simulator, typing a route on the device produces the
      same screen as the in-simulator CDU, key for key.
- [ ] Removing the screen name makes the feature unavailable with one plain sentence and no crash;
      removing one key name disables only that key.
- [ ] No log or message contains a token, protocol code or URL.

## Risks and open questions

1. The central unknown: whether Zibo publishes CDU screen text as datarefs at all. One report cites
   a `laminar/B738/fmc1/Line...` family [4]; the other found no confirmed names and notes that
   access has historically needed a UDP plugin [5]. Until this is settled on a running simulator,
   the feature stays conditional.
2. If the screen exists but the keys do not, or the reverse, the honest scope is a read-only mirror
   or nothing; both are acceptable answers to R1.
3. If the screen is published as one blob rather than lines, the delta-only subscription may carry
   the whole screen per keystroke. Latency needs measuring before responsiveness is promised.
4. Zibo renames datarefs between point releases, so a successful verification pins one version and
   must be re-run per release. Whether the two CDUs are separately addressable is unknown, and
   competing products with broad aircraft lists have gone stale; Avionix should not claim coverage
   it does not retest.

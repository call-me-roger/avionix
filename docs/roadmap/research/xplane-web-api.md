# X-Plane 12 Web API: Technical Landscape for a Companion App

Research date: 2026-09-15. Scope: what the official X-Plane 12 Web API (REST + WebSocket) can and cannot do for a monitor/control companion app (Avionix), what other projects have built on it, and open risks. Minimum supported sim version assumed: 12.1.4.

## A. Web API capability matrix

| Feature area | Support | How / notes | Source |
|---|---|---|---|
| Read datarefs (scalar, array, string, byte) | Supported | REST `GET /datarefs/{id}/value`; WebSocket `dataref_subscribe_values` streams updates at ~10 Hz, only changed values sent | [X-Plane local Web API](https://developer.x-plane.com/article/x-plane-web-api/) |
| Write datarefs | Supported (where dataref is writable) | REST `PATCH /datarefs/{id}/value`; WebSocket `dataref_set_values`; server returns `dataref_is_readonly` error otherwise | [X-Plane local Web API](https://developer.x-plane.com/article/x-plane-web-api/) |
| Dataref discovery/enumeration | Supported | `GET /datarefs` (list, filter, paginate), `GET /datarefs/count`; ids are stable only within a running sim session | [X-Plane local Web API](https://developer.x-plane.com/article/x-plane-web-api/) |
| Command discovery | Supported (since 12.1.4 / Web API v2) | `GET /commands`, `GET /commands/count` | [SDK Update: Web API v2](https://developer.x-plane.com/2025/01/sdk-update-web-api-v2/), [12.1.4 release notes](https://www.x-plane.com/kb/x-plane-12-1-4-release-notes/) |
| Command activation (press/hold/duration) | Supported | REST `POST /command/{id}/activate` (max duration 10 s); WebSocket `command_set_is_active` with `duration` (0 = press-and-release, omitted = held until explicitly deactivated, max 24 h); WS durations are cleared per-connection on disconnect | [X-Plane local Web API](https://developer.x-plane.com/article/x-plane-web-api/) |
| Command active-state subscription | Supported | WebSocket `command_subscribe_is_active` / `command_update_is_active` | [X-Plane local Web API](https://developer.x-plane.com/article/x-plane-web-api/) |
| Aircraft list/capabilities (REST) | Supported | `/aircraft`-style REST resource is documented as part of the API surface | [X-Plane local Web API](https://developer.x-plane.com/article/x-plane-web-api/) |
| Traffic (user + AI aircraft position) | Supported (REST + WebSocket) | Described in API overview as one of the four resource groups | search summary citing [developer.x-plane.com/docs/web-apis/](https://developer.x-plane.com/docs/web-apis/) |
| Weather (read/write, streamed) | Supported (REST + WebSocket) for the modelled weather state | Same API-overview grouping | [developer.x-plane.com/docs/web-apis/](https://developer.x-plane.com/docs/web-apis/) |
| Flight initialization (position/aircraft/weather/time/failures/AI) | Supported, v3, min 12.4.0 | `POST/PATCH /flight`; cannot change aircraft or start location mid-flight via PATCH | [Flight Initialization API](https://developer.x-plane.com/article/flight-initialization-api/) |
| Default X-Plane CDU/FMS screen text | Supported for the **default** FMS only | `sim/cockpit2/radios/indicators/fms_cdu{1,2}_text_line0..15` (24-char string lines) + matching `fms_cdu{1,2}_style_line0..15` byte-encoded style array (font size/reverse/flash/underline/color bits); available since X-Plane 11.35b5, exposed as ordinary datarefs so reachable over the Web API | [Datarefs for the CDU screen](https://developer.x-plane.com/article/datarefs-for-the-cdu-screen/) |
| Third-party (e.g. Zibo) CDU/FMS screen text | Not supported by Laminar; aircraft-specific, unofficial | Laminar's own CDU-screen article does not cover third-party FMSs; XPlaneCDU project notes "the default X-Plane 737 does not support this, and every other payware aircraft uses non-standard datarefs" | [XPlaneCDU README](https://github.com/waynepiekarski/XPlaneCDU) |
| Weather radar image/returns | Not supported via Web API | Reflectivity is exposed only as an 8-bit texture (`xplm_Tex_Radar_Pilot`/`_Copilot` via `XPLMGetTexture`), a **plugin-SDK-only** mechanism, not a dataref, and not reachable from REST/WebSocket | [Weather Radar for X-Plane 12.3](https://developer.x-plane.com/article/weather-radar-for-x-plane-12-3-1/) |
| Navdata / airport / navaid database queries | Not found in Web API | No REST/WebSocket endpoint for apt.dat/earth_nav.dat lookups was found in any fetched doc; this is a sim-internal database, not exposed | inference from [x-plane-web-api article](https://developer.x-plane.com/article/x-plane-web-api/) and [Web APIs hub](https://developer.x-plane.com/docs/web-apis/) (no such endpoint listed) |
| Flight-plan upload/edit via API | Not found as a Web API feature | Flight Initialization API configures the *starting* flight (position/weather/etc.), not an en-route FMS flight plan; no flight-plan-specific endpoint found | [Flight Initialization API](https://developer.x-plane.com/article/flight-initialization-api/) |
| Failures injection/read | Supported via ordinary dataref | `sim/operation/failures/failures` (int[564], read/write) plus per-system dataref groups; exact index-to-failure mapping is not fully documented by Laminar (a developer on the forum found it undocumented) | [forum: internal behavior of rel_engfai0](https://forums.x-plane.org/forums/topic/349281-internal-behavior-of-simoperationfailuresrel_engfai0-which-engine-parameters-do) |
| Sim control (pause/time/replay/view) | Supported via datarefs/commands, reachable over Web API | e.g. `sim/operation/pause_toggle` (command), `sim/time/paused` (read-only dataref), `sim/replay/*` commands | [Sim Innovations command search](https://siminnovations.com/wiki/index.php?title=Xplane_commandrefs) (community catalogue, not Laminar) |
| Remote (non-localhost) access | Not supported today; on roadmap | Server "is only listening for local connections for now"; Laminar states they "expect to extend to remote machines in the future" with an authorization popup UI, but connections today are unauthenticated by design | [X-Plane local Web API](https://developer.x-plane.com/article/x-plane-web-api/) |
| CORS headers for browser (web) clients | Not found / likely absent | No CORS headers are documented on the article; community guidance for browser callers is generic (proxy or `no-cors`), not an X-Plane-specific allowance | [X-Plane local Web API](https://developer.x-plane.com/article/x-plane-web-api/) (silence on CORS) |
| Authentication/token | Not implemented | "Right now the connections are unauthenticated" | [X-Plane local Web API](https://developer.x-plane.com/article/x-plane-web-api/) |
| Disabling the API server-side | Supported (by the sim operator) | Settings → Network → "Disable Incoming Traffic" returns 403 on all endpoints; `--no_web_server` launch flag disables the socket entirely | [X-Plane local Web API](https://developer.x-plane.com/article/x-plane-web-api/) |

## B. Datarefs and commands catalogue by feature area (default aircraft)

Every entry below is cited to its source; where I could not find a name in a fetched source I say so explicitly rather than guess.

**Autopilot**
- `sim/cockpit2/autopilot/heading_dial_deg_mag_pilot` — AP heading bug, pilot side — [Accessing the X-Plane autopilot from datarefs](https://developer.x-plane.com/article/accessing-the-x-plane-autopilot-from-datarefs/)
- `sim/cockpit2/autopilot/flight_director_mode`, `flight_director2_mode` — FD mode, pilot/copilot — same source
- `sim/cockpit2/autopilot/autothrottle_enabled` (−1 disarmed) and `autothrottle_arm` (0/1) — [Flight director and autothrottle datarefs](https://developer.x-plane.com/article/flight-director-and-autothrottle-datarefs/)
- `sim/cockpit2/autopilot/flight_director_command_bars_pilot` / `_copilot` — command-bar visibility toggles — same source

**Radios / transponder**
- `sim/cockpit2/radios/actuators/transponder_code` — transponder code, integer, current X-Plane 12 dataref (X-Plane 11 equivalent path was under a different actuator name) — search result citing MobiFlight/SPAD.neXt community docs, treat as community-sourced, not independently verified against Laminar's own list
- `sim/cockpit/radios/transponder_mode` — integer enum: 0 off, 1 standby, 2 on/Mode A, 3 alt/Mode C, 4 test, 5 GND Mode S, 6 TA-only Mode S, 7 TA/RA — community source (SPAD.neXt/MobiFlight docs), not confirmed against Laminar's own dataref list; treat as **inference/community**, not Laminar-verified
- `sim/atc/transponder_assigned` — ATC-assigned transponder code, added in X-Plane 12.4.4 — [X-Plane 12.4.4 Release Notes](https://www.x-plane.com/kb/x-plane-12-4-4-release-notes/) (name reported via search summary; recommend independently confirming exact path in-sim before shipping)
- `sim/cockpit2/radios/indicators/fms_cdu1_text_line0..15` / `fms_cdu2_text_line0..15` and matching `..._style_line0..15` — default FMS/CDU screen text and per-character style bytes (bit7 large font, bit6 reverse, bit5 flash, bit4 underscore, bits0-3 color) — [Datarefs for the CDU screen](https://developer.x-plane.com/article/datarefs-for-the-cdu-screen/)

**TCAS / traffic**
- `sim/cockpit2/tcas/targets/modeS_id[N]` — 24-bit unique target id, array up to 63 targets — [Overriding TCAS and providing traffic information](https://developer.x-plane.com/article/overriding-tcas-and-providing-traffic-information/)
- `sim/cockpit2/tcas/indicators/relative_bearing_degs`, `relative_distance_mtrs`, `relative_altitude_mtrs` — float[64] arrays — same source
- `sim/cockpit2/tcas/targets/position/...` — per-target position data, up to 63 other aircraft — same source
- `sim/cockpit2/tcas/targets/wake/wing_span_m`, `wing_area_m2`, `wake_cat`, `mass_kg` — wake-turbulence properties, X-Plane 12+ — [Overriding TCAS and providing traffic information](https://developer.x-plane.com/article/overriding-tcas-and-providing-traffic-information/); also see [TCAS resolution advisories and plugin traffic](https://developer.x-plane.com/article/tcas-resolution-advisories-and-plugin-traffic/)

These TCAS datarefs are primarily designed for *injecting* traffic (plugin-side), but since they are ordinary datarefs they should be *readable* by any dataref-capable client, including the Web API, to show traffic already present from AI/multiplayer/other plugins. Not independently confirmed by testing.

**Weather (aircraft position vs region)**
- `sim/weather/aircraft/*` — read-only, local weather at the aircraft's position (renamed from legacy `sim/aircraft/*` in the X-Plane 12 restructuring); individual sub-path names beyond this root were **not found** in the fetched article text — [Weather Datarefs in X-Plane 12](https://developer.x-plane.com/article/weather-datarefs-in-x-plane-12/)
- `sim/weather/region/change_mode`, `variability_pct`, `update_immediately`, `atmosphere_alt_levels_m` — writable regional weather controls — same source
- Cloud/wind/turbulence layers are "handled as real arrays" under `sim/weather/region/` rather than individually named datarefs; exact array dataref names **not found** in the fetched excerpt — same source

**Weather radar**
- No dataref exposes radar return/reflectivity data. Only a texture (`xplm_Tex_Radar_Pilot` / `xplm_Tex_Radar_Copilot`, read via `XPLMGetTexture()`) carries return-strength in the texture's red channel, and this is a native-plugin-SDK mechanism, unreachable from the Web API — [Weather Radar for X-Plane 12.3](https://developer.x-plane.com/article/weather-radar-for-x-plane-12-3-1/)
- Radar *controls* such as `EFIS_weather_mode`, `EFIS_weather_tilt` are ordinary datarefs and should be readable/writable over the Web API — same source

**Failures**
- `sim/operation/failures/failures` — int[564], read/write, one slot per modeled failure across roughly 14 system groups (engines, APU, electrics, hydraulics, fuel, flight controls, gear, anti-ice, air conditioning, fire, instruments, nav/comm, autopilot, airframe) — [forum: Failure dataref](https://forums.x-plane.org/forums/topic/39013-failure-dataref/), [forum: rel_engfai0 internals](https://forums.x-plane.org/forums/topic/349281-internal-behavior-of-simoperationfailuresrel_engfai0-which-engine-parameters-do)
- The exact index → failure-type mapping is **not fully documented by Laminar**; a plugin developer on the forum reported difficulty enumerating it from official docs. Any Avionix failures UI would need to either ship a community-sourced index table or read the (undocumented) per-system named datarefs individually.

**Sim control (pause / time / replay / view)**
- `sim/operation/pause_toggle` — command to toggle pause
- `sim/time/paused` — read-only dataref, 1 when paused
- `sim/replay/replay_off`, `rep_begin`, `rep_pause`, `rep_play_sf` / `rep_play_rf` / `rep_play_ff` — replay transport commands
- `sim/operation/screenshot`, `sim/operation/create_snap_marker` — utility commands
All from the community Sim Innovations command catalogue — [Xplane commandrefs — Sim Innovations Wiki](https://siminnovations.com/wiki/index.php?title=Xplane_commandrefs); this is a third-party mirror, not the Laminar-authored list, and names should be re-verified against the in-sim `Resources/plugins/DataRefs.txt`/`Commands.txt` before shipping.

**Engines / fuel / weights**
- `sim/flightmodel/weight/m_fuel[#tank]`, `m_fuel1`, `m_fuel2`, `m_fuel3` — fuel mass per tank, writable — [The X-Plane fuel system](https://developer.x-plane.com/article/the-x-plane-fuel-system/) (article referenced; exact per-tank dataref names as quoted come from a secondary community summary of that article, recommend re-confirming against the live DataRefs.txt)
- `sim/flightmodel/engine/ENGN_FF_*` — engine fuel-flow family — community summary citing the same DataRefs.txt convention; exact suffix/array shape **not independently confirmed** in this research pass

**Flight plan / FMS (default aircraft)**
- No REST/WebSocket endpoint or dataref for uploading/editing a route was found. The only FMS-adjacent Web API surface identified is the CDU screen text/style datarefs above (read-only visibility into what's already on the screen) and the general command set (which includes default-FMS button-press commands, not investigated dataref-by-dataref in this pass).
- Navdata (airports, navaids, procedures) queries: **not found** anywhere in the Web API docs. This lives in X-Plane's `apt.dat`/`earth_nav.dat` files and (optionally) Navigraph's own subscription/update pipeline, entirely outside the Web API's scope — inference from absence in [X-Plane local Web API](https://developer.x-plane.com/article/x-plane-web-api/) and [Web APIs hub](https://developer.x-plane.com/docs/web-apis/).

## C. Zibo 737 specific notes

- **Where the community dataref list lives:** the Zibo mod ships its own `B738_Datarefs.txt` / `B738_Commands.txt` alongside the aircraft; several community mirrors and tools (SimVimPanel, XHSI, MobiFlight forum posts, gists) republish subsets. See [Zibo 737 MCP panel dataref gist](https://gist.github.com/Klice/c21fec06f7f6e7d7e241468545b7468a), [XHSI_plugin datarefs.cpp](https://github.com/sum1els/XHSI_plugin/blob/master/datarefs.cpp), [cockpitbuilders.com Zibo FlightControl datarefs](https://www.cockpitbuilders.com/index.php?topic=7469.0). None of these are Laminar-authored; treat every Zibo path below as **community-sourced, unofficial, and subject to breakage on Zibo updates**.
- **Naming convention:** Zibo-specific datarefs use the `laminar/B738/...` prefix (e.g. `laminar/B738/autopilot/course_pilot`, `laminar/B738/autopilot/autothrottle_arm_pos`, `laminar/B738/autopilot/mcp_dial_kts_mach`, `laminar/B738/autopilot/bank_angle_pos`, `laminar/B738/autopilot/flight_director_pos`), while some standard AP parameters continue to use `sim/cockpit2/autopilot/...` or the copilot-side `sim/copilot/autopilot/...` / `sim/copilot2/autopilot/...` paths — [Zibo dataref gist](https://gist.github.com/Klice/c21fec06f7f6e7d7e241468545b7468a). By extension, MCP, EFIS and overhead panel controls are expected to live under `laminar/B738/<panel>/...` subtrees (e.g. presumably `laminar/B738/EFIS/...`, `laminar/B738/overhead/...`), but I did not find a complete enumerated list of those subtrees in this research pass — this is an **inference** from the one confirmed prefix pattern, not a verified catalogue.
- **CDU screen text:** Zibo does **not** use Laminar's default `fms_cdu1_text_line*` datarefs — its CDU is custom-rendered, and per the XPlaneCDU project README, "the default X-Plane 737 does not support this, and every other payware aircraft uses non-standard datarefs," with the linked bridge (ExtPanel v2, a third-party UDP plugin on port 51000, not the official Web API) providing access instead — [XPlaneCDU README](https://github.com/waynepiekarski/XPlaneCDU). No Zibo-specific CDU-line dataref names were found and confirmed in this pass; if Avionix needs Zibo CDU text over the Web API, this requires either (a) Zibo exposing its own text datarefs (unconfirmed) or (b) a separate plugin bridge, which falls outside the Web-API-only constraint.
- **Update churn:** Zibo is a fast-moving community mod with frequent point releases; its dataref/command lists have historically changed between versions (implied by the existence of multiple versioned community mirrors and forum threads tracking specific builds, e.g. [ZiboMod B737-800X v3.30+ installer notes](https://fsmagazin.de/download/ZiboModBoeingB737-800v330+.pdf)). Any Zibo-specific feature in Avionix should be built against a pinned Zibo version and treated as a compatibility-risk item requiring ongoing maintenance, not a stable contract like Laminar's own datarefs.

## D. Existing Web API projects

| Project | URL | What it does | Activity/notes |
|---|---|---|---|
| xpweb (Go) | https://pkg.go.dev/github.com/janeprather/xpweb | Go client library for the X-Plane 12 Web API | Found via package index; activity not verified in this pass |
| xplane-web-api (Rust) | https://github.com/leecbaker/xplane-web-api | Typed Rust REST client generated from an OpenAPI v3 spec (`xplane-web-api-v3.yaml`) plus optional typed WebSocket models and CLI | Minimal activity observed (1 star, 1 commit visible); useful mainly as a reference OpenAPI/AsyncAPI schema for the v3 API, dated ~Feb 2026 per search summary |
| xplane-proxy (CockpitConnect) | https://cockpitconnect.com/blog/xplane-proxy/ | Node.js utility run on the same machine as X-Plane that re-exposes the Web API's REST and WebSocket endpoints on `0.0.0.0` instead of `127.0.0.1`, so other LAN machines (e.g. hardware-cockpit PCs) can reach it | Explicitly built to work around the localhost-only bind; the blog post does not discuss security implications of doing this |
| XplaneRestApi | https://github.com/delacruz/XplaneRestApi | Older plugin exposing X-Plane variables via a RESTful service (predates the official Web API) | Predecessor-style project; relevant mainly as evidence of prior demand for REST access before Laminar shipped one |
| XPlaneConnect (NASA) | https://github.com/nasa/XPlaneConnect | Long-standing research toolbox (C/C++/Java/MATLAB/Python) for reading/writing datarefs and control over UDP, used heavily in aerospace research (not the official Web API) | Actively tracked for X-Plane 12 dataref compatibility, e.g. [Deprecated Data Refs for X-Plane 12, issue #286](https://github.com/nasa/XPlaneConnect/issues/286) and [PR #288 updating datarefs for XP12](https://github.com/nasa/XPlaneConnect/pull/288) — shows the pain of the UDP approach (datarefs move/rename between major versions) that the Web API's dataref-by-name-with-stable-session-id model is designed to reduce |
| ExtPlane | https://github.com/vranki/ExtPlane | Older UDP/TCP dataref bridge; per its own docs, UDP subscription only supports basic scalar types (int/float/double), no arrays or writes over UDP | [ExtPlane UDP.md](https://github.com/vranki/ExtPlane/blob/master/UDP.md) — useful contrast: the official Web API supports array and byte/"data" (base64) datarefs and read+write, which ExtPlane's UDP transport could not |
| xplanejs | https://github.com/balintb/xplanejs | Node.js module for X-Plane data; per search summary, currently read-only via UDP | Predates/parallels the Web API; not built on it |
| X-Plane/dashboard (Laminar) | https://github.com/X-Plane/dashboard | Laminar's own Plotly Dash webapp for X-Plane *usage/telemetry analytics* (product analytics, not a flight companion app) | Official Laminar repo, shows Laminar's own comfort with a web dashboard pattern, but is not a Web-API flight-instrument client |
| avionix (this project) | https://github.com/call-me-roger/avionix | The subject product itself — confirms via its own README that a mobile device on the same LAN can talk to X-Plane 12 through the built-in Web API, stream datarefs over WebSocket, write a dataref, and activate a command | Included for completeness; not an external comparator |

No other actively-maintained, general-purpose "companion app" (dashboard/remote panel) built specifically on the *official* 12.1.1+ Web API was found with a clear public repo in this pass beyond the above. The ecosystem is young — the official API itself only shipped in early 2025 (12.1.1) with commands added in 12.1.4 (Jan 2025) — so most public tooling is either (a) thin client libraries/SDK wrappers, (b) infrastructure like the LAN-exposure proxy, or (c) legacy UDP-era projects (XPlaneConnect, ExtPlane) still being retrofitted for X-Plane 12's dataref renames.

## E. Risks and open questions for a companion app

1. **Update-rate ceiling.** WebSocket dataref-subscription pushes are documented at "currently 10 Hz" ([X-Plane local Web API](https://developer.x-plane.com/article/x-plane-web-api/)). That is adequate for most instrument/autopilot/radio UI but may feel coarse for smoothly animated PFD needles/tapes; Avionix's roadmap should not promise frame-rate-matched instrument smoothness beyond ~10 Hz without client-side interpolation.
2. **No authentication, no CORS, localhost-only by design.** Today's server "only listens for local connections" and is explicitly "unauthenticated" ([X-Plane local Web API](https://developer.x-plane.com/article/x-plane-web-api/)). Any device other than the PC itself (i.e., every phone/tablet client) *must* reach X-Plane over the LAN, which the stock server does not support — this is presumably why Avionix already ships its own discovery/connector layer (per project history) rather than talking to X-Plane's server directly from a phone. Laminar has stated an intent to add LAN access with a user-facing authorization popup in the future, but this is **not shipped** as of the sources checked; the roadmap should not promise "connect directly to X-Plane's Web API from your phone" without a bridge/connector component, and should flag that Laminar's own future native LAN support could someday obsolete or need reconciliation with a custom connector.
3. **No browser CORS story found.** No documentation surfaced any `Access-Control-Allow-Origin` behavior for the Web API. An Expo web build calling `fetch()`/`WebSocket` directly against `http://<lan-ip>:8086` may hit CORS failures for the REST calls (WebSockets are less CORS-constrained but still origin-checked by some browsers/extensions); this needs empirical verification against a running 12.1.4+ instance, and likely requires routing web-build traffic through the same connector used for discovery rather than hitting X-Plane's HTTP server directly from browser JS.
4. **Session-scoped IDs.** Dataref and command numeric IDs are "not guaranteed to be the same the next time you start X-Plane" though stable within a session, including across aircraft loads/unloads ([X-Plane local Web API](https://developer.x-plane.com/article/x-plane-web-api/)). Avionix must resolve datarefs/commands by name at each connection/session start and cache IDs only per-session, never persist them across sim restarts.
5. **No official navdata/FMS-plan API.** Nothing found supports airport/navaid/procedure lookup or flight-plan upload via the Web API. Any GPS/FMS panel in Avionix limited to the official API can only *display what the sim's own FMS already shows* (default aircraft, via the CDU-line datarefs) and *cannot* build/edit routes, query the navdata database, or push a flight plan into the FMS. This is a hard roadmap constraint, not a "todo" — it would require either a separate plugin (out of scope per the Web-API-only constraint) or explicit product scoping to "mirror the existing default FMS screen" rather than "plan flights."
6. **No radar imagery / TCAS is default-aircraft-and-plugin-traffic-only.** Weather radar returns are only available as a plugin-SDK texture, unreachable from REST/WebSocket ([Weather Radar for X-Plane 12.3](https://developer.x-plane.com/article/weather-radar-for-x-plane-12-3-1/)); any weather-radar panel in Avionix cannot show real radar returns, only radar *mode/tilt/range* controls plus whatever regional weather datarefs it can read to fake a simplified rain overlay, which should be presented as an approximation, not a faithful radar.
7. **Zibo-specific panels are inherently unofficial and version-fragile.** Every Zibo dataref cited above comes from community mirrors, not Laminar; Zibo updates have historically renamed/restructured datarefs. Any Zibo-specific MCP/EFIS/overhead panel in Avionix needs an explicit compatibility-pinning and regression-testing story, separate from the "official API, any aircraft" baseline.
8. **Failures mapping is undocumented.** `sim/operation/failures/failures` is a 564-element array whose index-to-failure mapping Laminar has not published in an easily citable form; a forum developer confirmed this gap ([forum: rel_engfai0 internals](https://forums.x-plane.org/forums/topic/349281-internal-behavior-of-simoperationfailuresrel_engfai0-which-engine-parameters-do)). A failures panel would need to source (and maintain) a community index table, or fall back to per-system named datarefs only where those are documented.
9. **iOS local network permission.** Not X-Plane-specific, but relevant to the LAN-connection architecture generally: iOS gates local-network/Bonjour access behind a runtime permission prompt and `NSLocalNetworkUsageDescription`/`NSBonjourServices` entries; this affects any discovery/connector mechanism Avionix uses to find the sim host, independent of what the Web API itself supports. (General iOS platform behavior, not sourced from an X-Plane doc — flagged as background context, not a Web-API fact.)
10. **No confirmed built-in discovery of the Web API port.** The legacy UDP "BECN" beacon (multicast, historically port 49707) is a distinct, older mechanism for discovering a running X-Plane instance's UDP command port ([X-Plane discovery UDP BECN message thread](https://questions.x-plane.com/24465/plane-discovery-udp-becn-message-not-working-with-windows-10)); no source found in this pass confirms that BECN (or any other built-in broadcast) advertises the *Web API's* HTTP/WebSocket port specifically. Treat "the Web API is auto-discoverable on the LAN out of the box" as **not confirmed** — consistent with Avionix apparently needing its own discovery/connector mechanism.

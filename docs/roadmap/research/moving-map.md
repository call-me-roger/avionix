# F-13 Moving Map — Base Map Research

Researched 2026-10-07. Every claim below has a source URL. Where a tool could not reach a
source (forum/Reddit anti-bot walls, dead links), that is noted explicitly rather than
guessed at.

## 1a. Natural Earth (bundled offline vector data for react-native-svg)

- **License**: fully public domain. "All versions of Natural Earth raster + vector map data
  found on this website are in the public domain." Attribution is explicitly *not required*
  ("Crediting the authors is unnecessary"); an optional credit line is suggested: "Made with
  Natural Earth." Commercial and modified use is explicitly permitted.
  Source: https://www.naturalearthdata.com/about/terms-of-use/

- **Scales**: three fixed scales, each a separate hand-generalized dataset (not generated by
  decimating the 10m set):
  - 1:10m — "most detailed, for country/region maps"
  - 1:50m — "regional, tabloid-size" maps
  - 1:110m — "schematic world/postcard" maps
  Source: https://www.naturalearthdata.com/downloads/ (scale descriptions)

- **Physical vector dataset sizes** (Shapefile, current v5.1.x):
  | Dataset | 1:10m | 1:50m | 1:110m |
  |---|---|---|---|
  | Coastline | 2.93 MB | 445 KB | 83 KB |
  | Land | 3.12 MB | 446 KB | 68 KB |
  | Lakes + Reservoirs | 2.24 MB | 247 KB | 23 KB |
  | Rivers + lake centerlines | 1.98 MB | 493 KB | 30 KB |
  | Full physical bundle | ~50 MB | 7.25 MB | 3.27 MB |
  Sources: https://www.naturalearthdata.com/downloads/10m-physical-vectors/ ,
  https://www.naturalearthdata.com/downloads/50m-physical-vectors/ ,
  https://www.naturalearthdata.com/downloads/110m-physical-vectors/

- **Cultural vector datasets at 1:10m** (sizes shown, needed for later admin-0/places/airports
  work): Admin-0 Countries 4.7 MB (258 countries), Admin-0 Boundary Lines ~1 MB, Admin-1
  States/Provinces 14.2 MB, Populated Places 2.68 MB, **Airports 284 KB** (point layer — name/
  type only, no runway geometry), full cultural bundle 373 MB.
  Source: https://www.naturalearthdata.com/downloads/10m-cultural-vectors/
  (50m/110m cultural datasets exist too, proportionally smaller, same page family — not
  individually re-verified here since F-13 only needs coastline/land/lakes/rivers).

- **Positional accuracy in km**: **Natural Earth does not publish a formal accuracy spec in
  km.** Its "About" and FAQ pages describe the three scales only qualitatively (what they're
  "suitable for"), with no stated RMSE/tolerance.
  Source checked (no accuracy claim found): https://www.naturalearthdata.com/about/ ,
  https://www.naturalearthdata.com/downloads/ (FAQ URL
  naturalearthdata.com/about/faq/ 404s — page appears to have moved/been removed).
  If a number is needed for a design doc, the standard cartographic rule-of-thumb (0.5 mm
  line width at map scale) gives an order-of-magnitude estimate only — **~5 km at 1:10m,
  ~25 km at 1:50m, ~55 km at 1:110m** — but this is my own back-of-envelope conversion, not an
  Natural-Earth-published figure, and should be labeled as such if quoted anywhere.

## 1b. OurAirports (for later F-xx airport/navaid feature, not F-13 itself)

- **License**: public domain. "All data is released to the Public Domain, and comes with no
  guarantee of accuracy or fitness for use."
  Source: https://ourairports.com/data/

- **runways.csv DOES include runway end coordinates**: columns include
  `le_latitude_deg, le_longitude_deg, he_latitude_deg, he_longitude_deg` (plus elevation,
  true heading, displaced threshold for each end) — i.e. both ends of every runway are
  geo-located, not just the airport reference point.
  Source: https://ourairports.com/help/data-dictionary.html

- **airports.csv columns**: id, ident, type, name, latitude_deg, longitude_deg, elevation_ft,
  continent, iso_country, iso_region, municipality, scheduled_service, gps_code, icao_code,
  iata_code, local_code, home_link, wikipedia_link, keywords.
  Source: https://ourairports.com/help/data-dictionary.html

- **Sizes**: airports.csv ≈ 12.7 MB, runways.csv ≈ 4 MB, navaids.csv ≈ 1.5 MB,
  airport-frequencies.csv ≈ 1.3 MB — all well under what would be needed for an app bundle,
  but CSV, not a spatial index, so would need pre-processing (e.g. to a binary/SQLite tile
  format) before shipping.
  Source: https://ourairports.com/data/

## 1c. Online raster/vector tiles

- **OpenStreetMap tile policy (tile.openstreetmap.org)**: usable, but with hard constraints
  that make it a poor fit for a *distributed* mobile app:
  - Must send a distinctive `User-Agent` naming the app + contact info; generic/library
    default UAs are prohibited.
  - Must display "© OpenStreetMap contributors" attribution, not hidden/toggleable.
  - Must cache tiles locally and honor HTTP cache headers (or min. 7 days), use conditional
    requests — **no excessive re-fetching**.
  - **Bulk downloading, prefetching, and "offline packaging" of tiles is explicitly
    forbidden** — only tiles the user is actively viewing may be requested.
  - "Best-effort" service, no SLA; non-compliant traffic (generic UA, bulk patterns) is
    blocked without notice.
  Net effect: raw tile.openstreetmap.org is **not realistically usable for a shipped app**
  with many installs (one shared User-Agent from thousands of devices looks exactly like the
  abuse pattern it bans), and prohibits the offline caching an isolated-LAN sim app would want.
  Source: https://operations.osmfoundation.org/policies/tiles/ (the wiki page at
  https://wiki.openstreetmap.org/wiki/Tile_usage_policy now just redirects here).

- **OpenFreeMap**: no API key, no registration, no rate/usage limits stated ("no limits on
  the number of map views or requests" on the public instance). Serves **vector tiles**
  (static files) and also offers full-planet downloads (Btrfs/MBTiles) for self-hosting.
  Attribution requested but framed as optional/"nice to have": "OpenFreeMap © OpenMapTiles
  Data from OpenStreetMap." MIT-licensed infra, data under OSM's ODbL. Commercial use
  explicitly allowed. Caveat: it's a volunteer-run, donation-funded public instance with no
  SLA — fine for prototyping, risky to depend on for a shipped product without a fallback or
  self-hosting plan.
  Source: https://openfreemap.org/

- No other no-key raster/vector source was independently verified this session (web search
  tool quota was exhausted for this task — see note at bottom). Known-of-general-knowledge
  candidates worth a follow-up check: MapTiler's free tier (key required, so doesn't meet
  "no-key" bar), Stadia Maps free tier (key + attribution + domain allowlist), CARTO basemaps
  (now requires account/key for production). None of these were fetched/confirmed in this
  session — flag as unverified if used in the actual design doc.

## 1d. Native map libraries

- **@maplibre/maplibre-react-native**: latest published version **11.5.0** (released
  2026-10-04). peerDependencies: `react >= 19.1.0`, `react-native >= 0.80.0`; `expo >= 54.0.0`
  listed as an **optional** peer dependency (matches/undercuts Avionix's Expo SDK 57 / RN
  0.86 / React 19 stack).
  Source: https://registry.npmjs.org/@maplibre/maplibre-react-native/latest ,
  https://github.com/maplibre/maplibre-react-native/releases
  - **Expo**: has a dedicated Expo config plugin and an "Expo Setup" doc page, but it
    **cannot run inside Expo Go** ("This package can't be used with 'Expo Go'. It's not part
    of the Expo SDK.") — requires a custom dev client / prebuild, which Avionix likely
    already needs for other native modules.
    Source: https://maplibre.org/maplibre-react-native/docs/setup/expo
  - **New Architecture**: "From v11 onwards only the new architecture is supported" — i.e.
    v11.x *requires* Fabric/TurboModules, it isn't just an option.
    Source: https://maplibre.org/maplibre-react-native/docs/setup/getting-started
  - **Web support**: none. The project README describes itself as a "React Native library
    for creating maps with MapLibre Native for **Android & iOS**" — no react-native-web
    target.
    Source: https://raw.githubusercontent.com/maplibre/maplibre-react-native/main/README.md
  - **Offline packs**: supported — the API surface includes dedicated `OfflineManager` and
    `OfflinePack` modules (plus LocationManager, NetworkManager, StaticMapManager,
    TransformRequestManager), confirming native offline-region download/pack management is
    exposed to JS.
    Source: https://maplibre.org/maplibre-react-native/docs/modules/location-manager
    (sidebar nav lists all module pages)

- **react-native-maps**: latest version **1.29.11**. peerDependencies: `react >= 18.3.1`,
  `react-native >= 0.76.0`, and (new) `react-native-web >= 0.11` as an **optional** peer dep.
  Source: https://registry.npmjs.org/react-native-maps/latest
  - **iOS**: Apple Maps backend "works out-of-the-box" with no API key.
  - **Android**: "one has to use Google Maps, which in turn requires you to obtain an API
    key for the Android SDK."
    Source: https://raw.githubusercontent.com/react-native-maps/react-native-maps/master/docs/installation.md
  - **Web**: despite the `react-native-web` optional peer dependency appearing in package.json,
    actual web support is effectively **broken/unsupported in current versions** — a 2024-era
    GitHub issue "Please Bring Back Web Support" describes web rendering failing on both
    Metro and Webpack bundlers in v1.7.1/v2.0.0-beta, down from a last-working v0.31.1, and
    the maintainers offered no fix or workaround (issue is closed with no resolution shown).
    Source: https://github.com/react-native-maps/react-native-maps/issues/4735
  - New Architecture: per npm peer deps requiring RN >= 0.76 (Fabric default since RN 0.76),
    current releases target Fabric; not independently confirmed with a changelog quote this
    session.

## 2. What pilots/simmers actually say (verified subset — see caveat at bottom)

Reddit and x-plane.org forums could not be scraped directly this session (reddit.com returns
HTTP 403 to non-browser requests even with a spoofed desktop User-Agent; forums.x-plane.org is
behind a Cloudflare interstitial that blocks curl/WebFetch). The following is sourced instead
from the AviTab and Little Navmap open-source project trackers, which capture the same user
requests first-hand with permalinks:

- **North-up vs. heading/track-up is a live, named complaint.** AviTab GitHub issue #56,
  "[Feature Request] Add Track-Up / Heading-Up Map Orientation for VFR Navigation": "When
  flying VFR, pilots constantly compare the view outside the windshield with the map. If
  flying south with a North-Up map, left on the screen is right in the real world," and notes
  "most modern EFBs like ForeFlight, Garmin Pilot, or SkyDemon... offer Track-Up as a standard
  feature" — i.e. simmers explicitly benchmark companion-app maps against real-EFB behavior
  and currently AviTab only has north-up.
  Source: https://github.com/TeamAvitab/avitab/issues/56 (open)

- **Users and devs discuss adding more tile/map sources**, confirming AviTab's map is
  tile-based and extensible: issue #49 records a forums.x-plane.org community request to add
  Esri World Topo as a default slippy tile source; PR #48 removed X-Plane's own built-in map
  tiles as a source (kept external tile servers) while simplifying the build.
  Source: https://github.com/TeamAvitab/avitab/issues/49 ,
  https://github.com/TeamAvitab/avitab/pull/48

- **Little Navmap's own README confirms the AviTab-vs-LNM shape of the question**: LNM
  explicitly supports "OpenStreetMap as a background map which is only one option of many
  online and included offline maps," plus "its own internal web server which allows to follow
  aircraft progress from any device across a network" (the "Little Navmap web view" the brief
  asked about). This is the richer, multi-source, offline-capable map simmers compare AviTab's
  thinner single-tile-source map against.
  Source: https://github.com/albar965/littlenavmap
  (community add-ons like "LittleNavmapOFMTheme" — an Open Flightmaps VFR-chart theme for LNM
  — further show users actively adding VFR-chart-style overlays on top of the base map:
  https://github.com/AmbitiousPilots/LittleNavmapOFMTheme)

- **App Store reviews for Laminar's own X-Plane 12 Control Pad** (id 6701986565, 3.6★/23
  ratings) are sparse and skew toward connectivity/functionality complaints rather than map
  detail specifically — e.g. "after connecting to the sim all it will let me do is pause, quit
  xplane, shut down my computer, or adjust the app preferences" (1★). None of the 5 most
  recent reviews fetched mention the map by name.
  Source: https://itunes.apple.com/us/rss/customerreviews/id=6701986565/sortBy=mostRecent/json
  Its App Store release notes do confirm the map is airspace-aware: "Now with USA airspace on
  the map" (v1.05).
  Source: https://itunes.apple.com/lookup?id=6701986565&country=us

- **What this did not establish** (be explicit about the gap): I could not pull verified,
  quotable Reddit (r/flightsim, r/Xplane) threads or x-plane.org forum posts this session due
  to anti-bot blocking on both sites, and the WebSearch tool's session quota was exhausted
  before I could try alternate phrasings. The "needing internet on an isolated sim LAN" and
  "stale position" complaints specifically named in the brief are plausible (and consistent
  with the OSM tile-policy finding above, which structurally requires live internet per tile
  request) but I do not have a first-hand forum quote to cite for them — flag as needing a
  follow-up pass with a working search tool before stating them as sourced facts in a design
  doc.

## 3. Laminar's X-Plane 12 Control Pad and SimControlX — map provenance

- **X-Plane 12 Control Pad** (Laminar Research, iPad/iPhone, free, LAN-only companion to
  desktop X-Plane 12): App Store description: "Run X-Plane 12 for desktop Mac, Windows or
  Linux on your local LAN. Run this App on your iPad or iPhone on the same LAN!" — confirms
  it is a LAN-paired remote control, not a standalone app with its own persistent map tiles;
  release notes mention "USA airspace on the map," implying the map draws from X-Plane's own
  in-sim scenery/airspace data streamed over the LAN connection rather than a separately
  bundled or externally-tiled basemap. I could not reach a page that states the underlying
  map-rendering technology explicitly (Laminar doesn't document internals at that level
  publicly) — this is inferred from the product description and release notes, not a direct
  statement of "we use X." Flag as inferred, not confirmed.
  Source: https://itunes.apple.com/lookup?id=6701986565&country=us (description + release
  notes)

- **SimControlX**: **could not be reliably verified this session.** It does not appear in
  Apple's iTunes Search API under "SimControlX," "Sim Control X," or "aerosoft simcontrolx"
  (checked all three; no matching app in results). An Aerosoft shop page exists at a URL
  matching the product name (confirmed via a site search returning the page title "simcontrolx
  | Aerosoft Shop"), but the Aerosoft shop is a client-side-rendered SPA — curl only returns
  the shell HTML with no product data, and a direct WebFetch to
  `https://www.aerosoft.com/en/flight-simulation/apps/simcontrolx` returned **404** on a
  second attempt after an earlier attempt returned what looked like product detail (Wi-Fi
  server architecture, geo-referenced US IFR charts). Because of that inconsistency I am
  **not** reporting those details as confirmed — they may be a stale cache or a
  small-model fetch-summarizer hallucination rather than real page content. Recommend a
  follow-up with a working search engine or a direct browser check before citing anything
  specific about SimControlX's map source.

## Session tooling caveat

This session's WebSearch tool hit its call budget (200/200) almost immediately (likely shared
across prior work in this environment), before any query for this task completed. All
findings above come from direct WebFetch calls to known/guessed URLs and from GitHub's public
REST API via curl (not quota-limited). Bing, DuckDuckGo, and Ecosia were tried as WebFetch
targets to work around the missing search tool; all three returned geo-mismatched or
CAPTCHA-blocked results and were unusable. Where a claim could not be directly verified this
way, it is called out above rather than presented as fact.

## 4. Sizing measured for Avionix (2026-10-07)

Measured with a throwaway script over the GeoJSON in `nvkelso/natural-earth-vector` and the
OurAirports CSVs (`davidmegginson.github.io/ourairports-data`), quantising coordinates and
delta-encoding each ring as a JSON number array, after Douglas–Peucker simplification:

| Data | Quantum | Tolerance | Points kept | JSON size |
|---|---|---|---|---|
| 1:10m land | 1e-4° | 0.001° | 401,834 of 446,175 | 3.3 MB |
| 1:10m lakes | 1e-4° | 0.001° | 126,372 | 1.0 MB |
| 1:10m land borders | 1e-4° | 0.001° | 66,988 | 0.6 MB |
| 1:50m land | 1e-3° | 0.005° | 58,426 of 60,669 | 0.44 MB |
| 1:50m lakes | 1e-3° | 0.005° | 15,660 | 0.11 MB |
| 1:50m land borders | 1e-3° | 0.005° | 15,656 | 0.12 MB |

OurAirports: 14,867 open runways carry coordinates for both ends, at 11,364 airports.

Conclusion used by the F-13 spec: the 1:50m outlines plus runway geometry fit in about 1.4 MB of
JSON inside the app bundle; the 1:10m set (about 5 MB) does not, and would need a separate asset
pipeline.
